# M6-1: file Provider と prepared session

M6 の最初の単位。この文書は実装手順であり、完了条件は
[access.md](../access.md#m6-完了条件)、作業単位の位置づけは
[media.md](../media.md#作業単位)、contract 分類は [scope.md](../scope.md#m6-の-contract-分類)
を正本とする。

> 状態: **未着手**

## 目的

M5 の PCM 経路は application が渡した direct resource だけで動いており、`access.Reference`
から実際の byte session を開く経路が存在しない。M6-1 はその経路を作る。local file を
source と sink の両方で開き、Prepare が session を acquire して**宣言ではなく実際の**
capability を検証し、出力を temporary file と replace で commit する。

M6-1 は container を扱わない。WAVE、shared probe、Format inspect、spool は M6-2 以降が
担当する。したがってこの単位が終わった時点で動くのは「file から raw PCM を読み、file へ
raw PCM を書く」までであり、format 判別は explicit graph が担う。

## 決定

### canonical data unit schema の所有者と payload

- Access boundary の byte stream schema は `access.Bytes()` とする。消費側の二者
  （`plugin/file` は Access trait、Format component は `access.Alternative`）がどちらも既に
  `access` を import しているためで、`media/format` に置くと filesystem provider が media format
  を import することになる。
- `packet.Chunk` の schema は `media/format`、`packet.Packet` の schema は `media/codec` が
  所有し、`plugin/pcm/linear` の固有宣言を三つとも削除する。M6-2 の WAVE demux が出す chunk を
  PCM parser が受け取れること、codec Binding が format tag から parser を選べることが、schema
  identity の plugin 横断一致を前提にしているためである。三つを別々の単位で移すと同じ公開面を
  二度変えることになるので、この単位でまとめて移す。
- byte item の payload は `media/buffer.Handle` とする。`Fork` は `Share`、`Drop` は `Release`、
  `Size` は layout size。timestamp を持たないので `Time` は宣言しない。`[]byte` のままでは
  `Reader` が read ごとに所有権を渡すため buffer を再利用できず、boundary の payload だけが
  Job grant の外の GC allocation になる。
- したがって byte を produce する component は `Compile` で `resource.Request.Memory` を宣言し、
  `OpenContext.Buffers()` から確保する。宣言しないと `Buffers()` が nil になり Open で失敗する。

### write 側 capability と narrow view

- capability に `SequentialWrite` と `RandomWrite` を追加する。`Truncate` は temporary file
  へ新規に書く M6-1 の経路が必要としないため作らない。実 consumer が現れるまで語彙を増やさない。
- narrow view は read 側と同じく「宣言した操作だけを渡す」形にする。read 側が
  `Sequential`（`Read`）と `Random`（`ReadAt`）なので、write 側は `Appender`（`Write`）と
  `Patcher`（`WriteAt`）とする。`Writer` を使わないのは `flow.Writer[T]` が sink operator の
  意味で既に存在し、同じ語が二つの層で別の意味になるためである。
- view は `context.Context` を先頭引数に取る。read 側と同じく、cancel を stream 実装ごとの
  慣習ではなく contract にする。

### session の所有者

- acquire した session は `host.Prepared` が `reservations` と同じ場所で所有する。
  `internal/bound.Entry` は Bind 時に確定する immutable な記述のままとし、可変な session を
  持たせない。
- 専用の `internal/access` package は作らない。[access.md](../access.md#packagedistribution)
  のとおり、session の責務境界は shared probe と spool が入る M6-2/M6-3 の consumer を見て
  決める。M6-1 の時点で package 名を正本にしない。
- `Prepared.Close` と `Prepared.Run` の cleanup が、reservation と同じ bounded cleanup
  context で session を閉じる。閉じ漏れは cleanup failure として `Result` に出す。

### capability の再検証

- Provider manifest の `Capabilities` は planning のための宣言であり、acquire 後の session が
  実際に何を提供するかは session 自身が返す。両者が食い違った場合は Open 後の type assertion
  ではなく Prepare の構造化 diagnostic にする。
- **要求元を Format の方向別 trait へ移す。** M5 時点の `internal/bind.selectCapabilities` は
  Provider が自分で宣言した `Requirements` を自分の `Capabilities` に対して解決していた。
  M6-0 でその `Requirements` は削除済みなので、この単位が要求元を作る。`media/format` に
  read/write の `plugin.ComponentOption` を足し、boundary に隣接する component へ Format
  identity と方向別の alternative を付ける。binder は `format` の型付き accessor だけを読む。
- **alternative を `format.Format` から trait へ移す。** M5 時点の `Format` は方向を持たない
  単一の `[]access.Alternative` を持ち、どの component が消費するかも表せない。方向で要求が
  異なる以上この形では表現できないので、`Format` は identity、carrier、packetized だけを持つ
  方向中立な宣言に戻す。`Define` から alternative 引数が消え、`Define`/`DefinePacketized` の
  「片方は alternative 必須、片方は禁止」という非対称も解消する。
- **Probe/Inspect はこの単位で宣言しない。** 同じ trait へ後から足すが、形を決めるのは実
  consumer が現れる M6-3 とする。attachment point がこの単位で確定していれば、M6-3 は field を
  足すだけで済み、再設計にはならない。呼び出し元の無い function contract を二単位先取りしない。
- 出力側の alternative は M6-1 では file Provider が両方を提供するため常に第一 alternative が
  選ばれる。第二 alternative が実際に選ばれる経路は WAVE と spool が入る M6-2 で検証する。
  ここでは「選択が起きて `plan.Boundary.Selected` に出る」ところまでを固定する。

### transactional file output

- sink は target と同じ directory の temporary file を開く。commit は `os.Rename` とする。
  Windows でも `os.Rename` は `MoveFileEx` の `MOVEFILE_REPLACE_EXISTING` に写るため、
  既存 target がある場合も置換できる。外部 dependency を増やさないことを優先し、
  `ReplaceFile` による ACL/attribute の継承は必要になった時点で扱う。継承しないことを
  [capability.md](../capability.md#挙動変更の記録) へ記録する。
- transaction class は `AtomicReplace` とする。`PrepareCommit` で temporary file の close まで
  終え、`Commit` で rename、`Abort` で temporary file を削除する。
- `Flusher` と `Syncer` を実装し、Host の `Finalize -> Flush -> Sync -> PrepareCommit -> Commit`
  の順に乗せる。`Sync` は `File.Sync` を呼ぶ。
- cancel、Open 失敗、commit 失敗のいずれでも temporary file を残さない。既存 target は
  commit が成功するまで変更しない。

## 手順

### 1. canonical data unit schema を移す

- `access.Bytes()` を `schema.Type[buffer.Handle]` として追加する。`plugin/pcm/linear` の
  `Bytes`/`Chunks`/`Packets` と三つの marker を削除し、`media/format` と `media/codec` の
  vocabulary へ移す。互換の別名を残さない。
- linear の reader/writer と、それらを参照する test/Example を新しい schema へ移行する。
- `readerOperator` は `[]byte` ではなく handle を受け取る。framing が一致すれば所有権を move
  し、chunk 境界で分割が必要な場合だけ grant から確保して copy する。現在の
  `o.buffers.FromBytes(...)` が常に copy している経路を、必要な場合だけに狭める。
- `buffer.Handle` に部分範囲の view が必要になった場合は、その場で追加せず報告する。この単位で
  必要かどうかは実装して初めて分かるため、先に契約を広げない。

### 2. write capability と narrow view を追加する

- `access/capability.go` に `SequentialWrite`、`RandomWrite` を足す。
- `access/access.go` に `Appender`、`Patcher` を足し、read 側と対称であることを Example で示す。
- capability と view の対応（どの capability がどの view を渡せるか）を一箇所に置き、
  Provider 実装ごとの分岐にしない。

### 3. session acquire を Prepare へ入れる

- `host.Prepare` が bind 済み Provider boundary から session を acquire する段階を持つ。
  acquire は Prepare の中だけで行い、`Compile` は pure のままにする。
- `Host.Plan` は acquire した session を返す前に閉じる。read-only convenience である性質を
  変えない。
- `Prepared` が session を所有し、`Run` 完了と `Close` の両方で必ず閉じる。

### 4. Format を方向別 trait にし、capability 選択を要求駆動にする

- `media/format` に read/write の `plugin.ComponentOption` と型付き accessor を足す。M6-0 の
  `plugin.WithTrait`/`TraitValueOf` をそのまま使い、新しい機構を作らない。名前は `flow.Reader`/
  `flow.Writer` と衝突させないため動詞形（`format.Read`/`format.Write`、accessor は
  `format.ReadOf`/`format.WriteOf`）を既定とする。より適切な語があれば実装時に決めてよい。
- `format.Format` から alternative を取り除き、trait 側へ移す。`linear.Raw()` の宣言と、
  それを参照している test/Example を新しい形へ更新する。
- 付き先 component の shape と方向が食い違う trait を composition 診断にする。Access trait と
  同じ検査を `internal/catalog` の trait 走査へ足す。
- `internal/bind` の入力/出力 boundary が、隣接 component の Format trait が宣言した alternative
  を要求として `access.Select` に渡す。
- 選択結果を `plan.Boundary.Selected` に出し、満たせない場合は scheme、available、要求
  alternative を含む diagnostic にする。
- acquire 後の実 capability が宣言と異なる場合の diagnostic を追加する。

### 5. `plugin/file` を実装する

- source component: `file` scheme、`SequentialRead`/`RandomRead`/`StableSize`/`Reopen`/
  `CancelableRead` を宣言し、選択された view だけを operator へ渡す。読み出しは
  `Allocator.Overwrite` の write lease で grant memory へ直接読み込み、`Commit` した handle を
  emit する。短い read は block が埋まるまで読み継ぎ、末尾だけ実長で確保し直す。
- sink component: `SequentialWrite`/`RandomWrite` と `AtomicReplace` を宣言し、
  `Transaction`/`Flusher`/`Syncer` を実装する。
- どちらも `plugin.Component` として普通に宣言する。foundation package へ filesystem 実装を
  持ち込まない。

### 6. PCM 経路を file Reference で通す

- M5 の PCM skeleton test に、direct resource ではなく `file` Reference を使う経路を足す。
  direct resource 経路も残し、両方が同じ結果になることを検査する。
- bytes、item 数、順序、timestamp が direct 経路と一致することを固定する。

## 検証

```bash
go test ./access/ ./host/ ./internal/bind/ ./job/ ./plugin/file/ ./plugin/pcm/linear/ -race
go vet ./access/ ./host/ ./internal/bind/ ./job/ ./plugin/file/ ./plugin/pcm/linear/
go build ./...
gofmt -l .
go run ./tools/cmd/docs-check
```

追加で次を検査する。

- cancel、Open 失敗、`PrepareCommit` 失敗、`Commit` 失敗のそれぞれで temporary file が残らず、
  既存 target が変更されていない。
- 既存 target がある状態での commit が Windows と POSIX の両方で置換になる。
- `Host.Plan` が session を閉じ、output を作成も truncate もしない。
- 宣言 capability と実 session capability が食い違う fixture Provider で、Prepare が構造化
  diagnostic を返す。
- boundary component の port schema が `access.Bytes()` でない場合、Host 構築が composition
  diagnostic で失敗する。
- file 経路の byte payload が Job grant に計上され、Run 終了時に返却される。`Prepared` の
  reservation 検査が「payload allocator retained N bytes」を報告しない。

単位完了時は [access.md](../access.md#m6-完了条件) のうち M6-1 が担当する行
（file Provider、session acquire、実 capability 再検証、write capability/view、
transactional file output）を実装と test へ対応付ける。probe、inspect、spool、quota は
M6-2/M6-3 の担当として未着手のまま残す。
