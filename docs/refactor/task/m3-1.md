## M3 全体の分割

M3 は package 数が M2 の 3 倍以上ある。[media.md](../media.md#m3-完了条件) が walking skeleton を要求する理由が「consumer のいない contract を積み上げない」ことなので、skeleton を最初に通し、以降の単位でそこへ足す順序にする。

| 単位 | 内容 | 指示書 |
|---|---|---|
| M3-1 | 縦断経路に必要な最小の型と walking skeleton | この文書 |
| M3-2 | metadata model と Binding。skeleton に metadata 経路を足す | M3-1 完了後に作成 |
| M3-3 | 残る拡張点の網羅と、consumer を持たない contract の一覧化 | M3-2 完了後に作成 |

前の単位が通した skeleton を後の単位が壊さない。単位をまたいで未完成の型を残さない。

## 着手前に確定した判断

M3 の設計文書に留保として残っていた 4 点を確定済みである。実装中にこれらを覆さない。

1. **`component` package を新設しない。** component Spec は `plugin.Component` が持つ。理由は [C21](../decisions.md#c21-foundation-package-は-media-領域だけを-grouping-する)。
2. **component Spec のうち M3 が確定するのは port shape と `Open` まで。** `Compile` と `Suggest` は planner という consumer が入る M4 が確定する。
3. **typed frame は `media/audio` だけを作る。** `media/video` と `media/subtitle` は実 consumer が現れるまで作らず、第三者相当の schema fixture で拡張性を検査する。
4. **動的 `Shape` phase は M4 が扱う。** M3-1 は静的 port shape だけを作る。config が port 数を決める component（mixer 等）は planner 側にしか consumer がなく、[checkpoint.md](../checkpoint.md) の申し送りどおり port 数の出所は `Shape` を実際に使う milestone で決める。

## スコープ

**やること**: foundation の新 package 新設と、M2 の `plugin.Component` 拡張のみ。

**やらないこと**:

- `core`、`sdk`、`plugin/<family>`、`cli`、`bindings`、`example` の変更。旧経路はそのまま動かし続ける。
- planner、solver、`Plan`、`Program`、scheduler、queue、execution island（M4/M5）。
- `Compile`、`Suggest`、動的 `Shape`、variant、`resource`、`job`（M4/M5）。
- metadata Document/Origin/RawBlock/Mapping/tag/metadata Binding（M3-2）。
- `media/side`、`endpoint`、Device、`access.Reference`/`Provider`、transaction class、spool、bounded Probe の実装、`stream.Event` と `FiniteStatic`/`LiveStatic`/`LiveDynamic`（M3-3）。
- 実 Format/Codec の実装、`standard`、`integration`、`testkit`（M6 以降）。

将来 phase 用の空 field、placeholder interface、TODO 付きの型を先回りして作らない。

## package 配置

root module (`github.com/godexture/godec`) に置く。`go.work` の変更は不要。配置は [C21](../decisions.md#c21-foundation-package-は-media-領域だけを-grouping-する) に従う。

```text
media/timing/     time base、typed PTS/DTS/duration、checked rescale
media/schema/     open typed schema、trait、typed runtime factory
media/property/   immutable open property key/set
media/stream/     stream descriptor
media/packet/     container chunk と codec packet
media/buffer/     aligned backing buffer、plane layout、ownership handle
media/audio/      typed sample frame
media/format/     Format contract、Carrier 宣言、capability alternative
media/codec/      Parser、Parameters、container codec Binding
flow/             typed port、Reader/Writer、Processor/Operator、Input/Emitter
access/           byte source/sink capability、Own/Borrow/Factory
plugin/           既存 package に port shape と Open を追加
```

package 名は複合語を避ける（[AGENTS.md](../../../AGENTS.md) Rules）。

## 作業単位と手順

単位ごとに独立して review・commit できる粒度を保つ。各単位は「実装 → その package の test → 次へ」の順で進める。

### 1. docs link/anchor gate

[quality.md](../quality.md#repository-wide-ci) は `documentation` gate のうち link と anchor の検査を **M3 から**実行すると定めている。M3 は文書の相互参照が最も増える milestone なので、他の作業より先に用意して以降の単位を保護する。

- `docs/` 配下の Markdown を対象に、相対 link の解決先 file と `#anchor` の存在を検査する command を `tools/cmd` へ追加する。
- anchor は GitHub の heading slug 規則に合わせる。日本語 heading を含むため、実際に `docs/refactor/` の既存 link が全て通ることを検査の正しさの根拠にする。
- 失敗は「どの file のどの行の、どの link が、なぜ解決できないか」を出す。件数だけを返さない。
- snippet compile と example consistency は M10 の担当なので実装しない。

### 2. `media/timing`

以降の全 package が依存する。

- stream ごとに一つの integer time base を持つ。rational を control plane で使えるが、item ごとに arbitrary precision arithmetic を使わない。
- PTS、DTS、duration を **型として区別**する。相互代入を compiler が拒否する形にする。
- rescale は checked integer arithmetic とし、overflow を error にし、rounding policy を呼び出し側が明示する。暗黙の切り捨てを既定にしない。
- timestamp 不明を `0` と混同しない optional/flag を持つ。`0` は有効な timestamp である。
- property/fuzz test で overflow 境界、負値、rounding tie、極端な time base 比を検査する。

### 3. `media/schema`

- `Define[ID, T]` が marker 型 `ID` から identity を導出し、payload 型 `T` と分離する。`T` の refactor が identity を変えない。
- `Type[T]` は identity と runtime trait を持つ。trait（`Fork`、`Drop`、`Size`、`Time`）は必要な時だけ呼ぶ。観測や byte limit が無効な linear path で `Size` を毎回計算しない。
- 型消去は descriptor が保持する generic factory closure に限定する。`T` が確定した状態で `pipe[T]`、tee 等を作る closure を登録し、catalog/planner は erased descriptor だけを持つ。
- item ごとの reflection、文字列 lookup、`any` map、serialize を要求しない。type assertion は Open 時に一度だけ行う形にする。
- core が `T` を事前に知らなくてよいことを、第三者相当の marker と payload 型を使う test で検査する。

`schema` の trait 関数は media 専用の意味を持たない。非 media schema の第三者 unit にも同じ仕組みで宣言できることを test の一部にする。

### 4. `flow`

- port は schema の具体型で結ぶ。`In(schema)` / `Out(schema)` 相当と、静的な `Shape`、`Inputs`/`Outputs` を持つ。
- port は schema identity、required/optional、multiplicity（one / optional / many）を宣言できる。fan-in policy、ordering/timing requirement、dynamic shape 可否の宣言は M4 が使うため、この単位では最小の型に留めるか置かない。
- 一 item の変換を書く `Processor[I, O]` と、typed Reader/Writer を扱う `Operator` の両方を持つ。両者は同じ port/schema/lifecycle を使い、別 runtime を作らない。
- `Input[I]` は借用 view とし、`Value()`（呼び出し中だけ読む）、`Take()`（ownership を取得）、`Share()`（retained handle）を明示する。plugin author に `Retain`/`Release` と refcount を触らせない。
- ownership 規則を godoc に固定する。Reader が返した時点で consumer へ move、Writer 成功時に writer へ move、Writer 失敗時は呼び出し元が保持（[runtime.md](../runtime.md#ownership)）。
- plugin contract に channel を露出しない。queue、goroutine、scheduler をこの package に持ち込まない。

### 5. `plugin.Component` の Spec 化

M2 の `plugin.Component` へ port shape と `Open` を足す。後方互換の signature は残さない。

- 既存の identity、descriptor、型消去 config schema、alias、provenance、diagnostic 集約はそのまま保つ。
- port shape を持ち、`internal/catalog` が host 構築時に検証する。schema 不一致、required port 未接続のような graph 検証は M4 の担当だが、port shape 自体の妥当性（空、重複 port ID、未定義 schema）はここで失敗させる。
- `Open` は選択済み component を一度だけ runtime operator にする。narrow service を引数で渡す形にし、全 service を引ける service locator を渡さない。M3 時点で渡す service が無いなら引数を作らない。
- `Compile` の field をこの単位で作らない。M4 が追加する。

### 6. `media/property` と `media/stream`

- `property.Set` は immutable な control-plane 値とし、typed key で保持する。key は marker 由来にして第三者が core 無変更で追加できる。
- 未知 property を解釈せずに保持・複製できる。component は requirement として宣言した property だけを解釈する。
- `stream.Descriptor` は schema identity、time base、`property.Set` を持つ。`metadata.Document` field は M3-2 が足す。
- 閉じた stream kind enum と、全属性を詰め込んだ属性 struct を作らない（F5）。
- hot path の unit が property map を持たないこと、stream-local な不変情報が descriptor 側にあることを設計で示す。

### 7. `media/packet`

- container が読む単位（chunk）と decoder が要求する単位（packet）を**別の型**にする（F20）。
- packet は PTS/DTS/duration を `media/timing` の optional 型で持ち、payload は `media/buffer` の ownership handle で持つ。
- bitstream filter を `Packet -> Packet` の component として表現できる形にする。
- EOF を data sentinel で表さない。`PacketKindStreamEnd` 相当の値を作らない（F24 の再発防止）。edge close で表す前提を godoc に書く。
- side data field はこの単位で作らない。`media/side` は M3-3。

### 8. `media/buffer` と `media/audio`

`media/audio` を先に作る理由は [media.md](../media.md#m3-完了条件) に記載した。

- `buffer` は可能なら plane ごとの別 allocation を避け、一つの aligned backing buffer と plane offset を持つ。alignment、plane size/padding、read-only/shared flag を扱う。
- allocator/pool の実装を plugin へ公開しない。`Frame[S]` は backing buffer の ownership handle を持つ。allocator 本体は M5 の `internal/memory`。
- `audio.Frame[S Sample]` は PTS、sample count、owned planes のような item-local 情報だけを持つ。sample rate、channel layout、valid bits は `stream.Descriptor` の property に置き、frame ごとに複製・再検証しない。
- planar を canonical representation とする。packed/interleaved が必要になった場合は別 schema/型にする。
- 検証は境界へ集約する（F27）。frame 構築時に plane count、plane length、sample count、alignment、buffer bounds を検査し、hot loop で再検証しない。
- midstream format change を frame field の変更で表さない。

### 9. `access` の最小形

この単位が担当するのは byte capability と ownership だけである。`Reference`、`Provider`、transaction class、spool、bounded Probe は M3-3。

- capability を巨大な boolean struct にせず、sequential read、position-independent random read、stable known size のような小さな contract の組み合わせで表す。
- random read は共有 cursor の `Seek` より `ReadAt` 相当を優先する。
- component には宣言した requirement を満たす **narrow view だけ**を渡す。不可能な operation を nil field として渡し、plugin 内で type assertion させる余地を型で消す（F18）。
- `Own`（Host が閉じる）、`Borrow`（Host は閉じない）、`Factory`（Prepare ごとに新しい owned session）で ownership を明示する。blocked I/O を cancel で解除できるかを capability に出す。単なる `io.Reader` を context-aware と偽らない。
- foundation package が filesystem、network、device の具体実装を import しない。

### 10. `media/format` と `media/codec`

- Format は byte 列の framing/stream table/header/footer を読み書きする。byte 列の所在（file/HTTP/S3/memory）を扱わない。特定 decoder、metadata parser、Access Provider を import しない構造にする。
- Format は capability alternative を宣言できる（例: `sequential` または `random + stable size`）。capability 不足が Open 後の type assertion ではなく宣言として現れる。
- Carrier を宣言できる。format-owned だけでなく codec/bitstream-owned carrier もあるため、単一の owner ID を埋め込まない。payload の意味は Carrier が決めない。
- Parser を第一級 component として宣言できる。すでに packetized された container では identity または不要にできる。
- `codec.Bind(formatTag, codec, parser)` 相当の Binding を composition 時に登録できる。Binding は `plugin.Set` に入り、**同じ binding key が異なる対象を指す場合に `host.New` が失敗する**。暗黙の last-wins を使わず、意図的な置換は明示 override だけで行う。
- Probe/Inspect は contract として宣言するだけでよい。実行する consumer は M4 の Prepare である。

### 11. walking skeleton

M3-1 の受け入れの中心である。foundation の test 内に置き、公式 plugin を import しない。

- test 用の trivial な schema、format、codec を定義し、`bytes → chunk → packet → frame → packet → chunk → bytes` を新 contract だけで端から端まで流す。
- component は `plugin.Set` へ入れ、`host.New` で検証済み catalog にしてから `Open` で operator を取る。test が持つのは駆動 loop と接続順だけとする。planner と runtime を使わない。
- codec Binding の conflict が `host.New` の error になることを、同じ経路で検査する。
- 出力 bytes が入力 bytes と一致することだけでなく、途中の timestamp、item 数、順序が保たれることを検査する。
- 第三者相当の非 audio schema（`video.Frame`/`subtitle.Cue` 相当）を core 無変更で宣言し、port を結べることを別の test で検査する。package は作らない。
- この経路は M3-2 が metadata を足し、M4/M5 が planner/runtime を差し込み、M6 が実 WAVE/PCM へ置換する。**壊さずに拡張できる形にする。**

### 12. 分類の記録

[media.md](../media.md#m3-完了条件) が求める「walking skeleton が実際に使う contract」と「宣言だけで consumer を持たない contract」の分類を、[scope.md](../scope.md) へ節として追記する。M3-1 の範囲だけを書き、M3-3 が完成させる。

consumer を持たない contract は型を最小限にとどめ、詳細を凍結しない。

## test

各 package に unit/property test を置く。公式 plugin を import しない。test 用の schema/component/format/codec は foundation test 内の fixture として定義する。

[quality.md](../quality.md#foundation-test) の一覧のうち、この単位で該当するのは次である。

- typed schema registration と unknown schema
- checked timestamp rescale、overflow、rounding
- ownership move、fan-out、write failure、drop
- codec Binding conflict
- 第三者相当 schema の追加が core 変更を要さないこと

race test を実行する。map iteration order と registration order を意図的に乱す test を含める。

## 検証

[AGENTS.md](../../../AGENTS.md) の Tools と [quality.md](../quality.md#開発時の検証-tier) に従う。

- 単位ごと: 対象 package の test。例 `go test ./media/... ./flow/... ./access/... ./plugin/ -race`
- 単位ごと: `go build ./...`（新 package が root module の build を壊していないこと）
- 単位 1 の後: 追加した docs gate を `docs/` 全体に対して実行し、既存 link が全て通ることを確認する
- M3-1 完了時: `go run ./tools/cmd/test-runner --simd`。exit status を直接確認し、`tail` 越しの exit code で判定しない

benchmark はこの単位で取らない。data plane の実行が入るのは M5 である。ただし hot-path 性能契約（[runtime.md](../runtime.md#hot-path-性能契約)）に反する形——item ごとの reflection、`any` map 走査、interface lookup、必須 atomic、node ごとの goroutine/channel——を contract へ持ち込まないことを review 観点にする。

## 中断して確認する条件

[AGENTS.md](../../../AGENTS.md) の規約どおり、次の場合は独断で決めずに実装を止めてユーザーへ確認する。

- 参照文書の記述どうしが矛盾する、または M3 の完了条件を満たす方法が複数あり、どちらも public contract の形を変える。
- 「着手前に確定した判断」の 4 点のいずれかが、実装上成立しないと判明した。
- walking skeleton を通すために M4/M5 の型（`Compile`、`Plan`、queue、scheduler）が必要だと判明した。
- 新 package の contract を成立させるために `core`/`sdk`/`plugin/<family>` の変更が必要だと判断した。
- [decisions.md](../decisions.md) にない product 判断が必要になった。この場合は decision ledger の「更新規則」に従い、確認待ちとして記録する。

## 完了時の記録

1. [media.md](../media.md#m3-完了条件) の完了条件のうち、この単位が担当する項目を逐条で確認する。満たせない項目があれば完了にせず報告する。M3-2/M3-3 が担当する項目と取り違えない。
2. `go run ./tools/cmd/test-runner --simd` を実行する。
3. [checkpoint.md](../checkpoint.md) の M3 行を更新する。更新規則はその文書の冒頭に従い、benchmark の単発値や test log を残さない。
4. M3-2 へ送る事項があれば、この文書ではなく該当設計資料または checkpoint の注記へ書く。
