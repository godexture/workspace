# M6-0: 合成 contract の是正

M6 の最初の単位。M6 着手時の contract 監査で見つかった不整合を是正する。この文書は実装手順
であり、完了条件は [access.md](../access.md#m6-完了条件) の trait 化条項と
[plugins.md](../plugins.md#m6-完了条件) の合成条項、作業単位の位置づけは
[media.md](../media.md#作業単位) を正本とする。

> 状態: **未着手**

## 目的

M4 で置いた合成 contract が、M6 の最初の実 Provider を表現できないことが着手前監査で判明した。
この単位はその 2 点だけを直し、新機能を作らない。data path は M5 のまま変わらず、M6-1 が
file I/O を足せる状態にして終わる。

## 是正する不整合

### 1. Provider が source と sink を同時に提供できない

`access.Provider` は component identity を一つしか持たない。一方 `internal/bind.boundaryPort`
は input boundary に 0-in/1-out、output boundary に 1-in/0-out を要求する。静的 shape で
両方を満たす component は存在しないため、同じ `file` scheme で source と sink を提供できない。
`internal/bind.Registry.providers` も `map[string]access.Provider` で scheme ごとに一つなので、
source 用と sink 用を別 Provider として登録する回避もできない。

`ProviderRole` の `SourceSinkRole` は構築でき `AllowsSource`/`AllowsSink` も真を返すが、
実際に bind されることは決してない。`access` の既存 test はその manifest を構築して
`Declarations()` の件数だけを検査しており、両方向が bind できるかを一度も確かめていない。

### 2. 合成が一つの値にまとまらない

`plugin.Declaration` は key と target と problem だけを持つメタデータで、振る舞いを持たない。
`plugin.Set` は definition と declaration しか保持しないため、Provider を運べない。
`host.New` は Provider を別 option で受け取り、catalog 検証用の Declaration だけを取り出して
いる。

`plugin` 側に型付きの Provider carrier を置くことはできない。`access` が `plugin` を import
しているため循環になる。

### 3. 合成 API が利用者へ拡張の分類を漏らす

Provider と Endpoint を `host` の独立 option として受け取る形にすると、第三者が Format と
Provider を含む plugin を配ったとき、利用者は `host.Plugins` と `host.Providers` の使い分けを
知る必要がある。foundation の分類学が利用者コードへ漏れており、`host.New(append(base,
host.Plugins(acme.Plugin()))...)` のような定型句も伴う。1 と 2 を直しても、この 3 は残る。

## 決定

### Access と Endpoint を component の trait にする

三つの不整合を個別に直すのではなく、拡張の宣言場所を変えることで同時に解消する。Provider と
Endpoint を独立した合成入力にせず、**宣言する対象の component に付く `plugin.ComponentOption`**
にする。

- これは新機構ではない。M5 の `plugin.WithReader`/`WithProcessor`/`WithWriter` が typed
  execution binding を component へ付けたのと同じ形を、もう一種類へ適用する。`plugin` に増える
  のは marker key 付きの trait slot 一つだけである。
- slot の値は型消去になる。`access` が `plugin` を import しているため型付きにはできない。
  ただし取り出し口は `access`/`endpoint` が型付き accessor として提供し、`host` と
  `internal/bind` に kind ごとの type switch を残さない。これは `plugin.ExecutionOf` が `any`
  を返して `internal/run` が一度だけ assert する既存の形と同じである。
- 値は composition と Prepare でしか触らず、item 経路には現れない。
- 第三者が拡張できるのは trait の**実装**であり**種類**ではない。host が解釈するのは Access と
  Endpoint の二種だけで、未知の trait 種は解釈しない。この閉じた集合であることを文書に明示する。

これにより不整合 1 は構造的に消える。source trait は 0-in/1-out の component、sink trait は
1-in/0-out の component に付くため、方向は付き先が決める。不整合 2 と 3 も消える。trait は
component に載り、component は definition に、definition は `Set` に載るので、`plugin.Set` が
唯一の合成値になる。

### 削除するもの

互換のための経路を残さず、この単位で消す。

- `access.ProviderRole`（`SourceSinkRole` を含む）。方向は trait の付き先から導出する。
- `access.Provider` の manifest 形と、それが自分で declaration を生成する経路。
- `access.Provider.Requirements`。byte を消費するのは Format/component 側であり、Provider が
  自分の要求を自分の capability に対して解決する形は意味を持たない。要求元の移動は M6-1 が
  担当するので、この単位では削除と、選択が行われない状態の診断までとする。
- `endpoint.Component`（plugin component と trait の対を作る型）。
- `host.Providers` / `host.Endpoints` option。
- `internal/bind.NewRegistry` の「Provider component が catalog に無い」「Endpoint manifest が
  catalog component を記述していない」検査。trait が component 上にあるため表現不能になる。

### acquire を trait の操作にする

- session を開くのは Prepare の段階であり、component の `Open` ではない。したがって acquire は
  宣言ではなく trait が持つ操作にする。
- この単位では acquire の**契約だけ**を置き、実装は `plugin/file` を作る M6-1 が最初の
  consumer になる。宣言だけを増やさないため、契約の形は M6-1 の手順で必要になるもの
  （`Reference` と選択済み capability を受け取り、閉じられる session を返す）に限定する。

### scheme の衝突検出

- `internal/catalog` が component の trait を走査して scheme の重複を検出する。codec/metadata
  Binding と同じ composition 診断の channel に載せ、Access 専用の registry を新設しない。
- 同じ scheme に同じ方向の trait が二つある場合だけ衝突とする。source と sink が同じ scheme を
  持つのは正常である。

### `standard` はこの単位で作らない

実 family が無い状態で composition package を置くと consumer の無い export になる。
`standard.Set()` と `NewHost()` の形は M6-4 が実 family とともに作る。この単位で確定させるのは
trait 契約と `host` 側の option 契約だけである。

## 手順

### 1. `plugin` に trait slot を足す

- marker key で引ける component trait slot を `componentOptions`/`Component` へ足す。同じ key
  が二度付いた場合は composition 診断にする。
- 低レベルの付与と取り出しだけを公開し、`plugin` は Access/Endpoint の意味を知らないままにする。
- `WithReader` 等の既存 option と並べても意味が重複しないことを Example で示す。

### 2. Access と Endpoint の trait を定義する

- `access` に source trait と sink trait の `plugin.ComponentOption` を足す。scheme、capability、
  transaction class、acquire 契約を持たせる。付き先 component の shape が方向と一致しない場合は
  composition 診断にする。
- `endpoint` の trait を同じ形の option にし、`endpoint.Component` を削除する。
- 型付き accessor を `access`/`endpoint` に置き、`host`/`internal/bind` はそれだけを呼ぶ。
- `SourceSinkRole` を構築していた test を、同一 scheme の source/sink trait が実際に両方向へ
  bind されることを検査する test へ置き換える。manifest の件数だけを見る検査を残さない。

### 3. catalog と binding を trait 駆動にする

- `internal/catalog` が trait を走査し、scheme 衝突と付き先 shape の不一致を検出する。
- `internal/bind` は catalog から方向に応じた trait 付き component を引く。`Registry` が
  `[]access.Provider` を受け取る形と `AllowsSource`/`AllowsSink` の分岐を削除する。
- その方向の trait を持つ component が無い scheme を指定した Job は、構造化 diagnostic で
  拒否する。

### 4. 合成 option と影響範囲を整える

- `host.Providers`/`host.Endpoints` を削除し、`host.New(host.Plugins(set))` だけで Access と
  Endpoint を含む合成が成立することを test で固定する。
- `plan.Boundary.Component` は方向に対応する component identity を指すようになる。Plan
  fingerprint への影響を test で固定する。
- `access`/`endpoint`/`host` の Example と binding test を新しい形へ更新する。互換のための旧
  API を残さない。

## 検証

```bash
go test ./access/ ./endpoint/ ./host/ ./internal/bind/ ./internal/catalog/ ./plan/ ./plugin/ -race
go vet ./access/ ./endpoint/ ./host/ ./internal/bind/ ./internal/catalog/ ./plan/ ./plugin/
go build ./...
gofmt -l .
go run ./tools/cmd/docs-check
```

追加で次を検査する。

- 一つの scheme に source trait と sink trait を持つ composition が、input boundary と output
  boundary の両方で実際に bind される。宣言の検査だけで済ませない。
- その方向の trait を持つ component が無い scheme を指定した Job が、構造化 diagnostic で拒否
  される。
- 方向と付き先 component の shape が食い違う trait が、host 構築時に診断される。
- **`host.New(host.Plugins(set))` だけで Access/Endpoint を含む合成が成立する。** 第三者相当の
  Provider を持つ definition を `Set.Add` するだけで bind されることを test にする。合成 option
  を種類ごとに使い分けない。
- M5 の PCM walking skeleton と host lifecycle/failure matrix が引き続き green である。
  この単位は data path を変更しない。

単位完了時は、[access.md](../access.md#m6-完了条件) の trait 化・削除・acquire・scheme 衝突の
4 行と、[plugins.md](../plugins.md#m6-完了条件) の合成 4 行を実装と test へ対応付ける。
file Provider の実装、session の実 acquire、capability 要求元の移動は M6-1 の担当として未着手の
まま残す。
