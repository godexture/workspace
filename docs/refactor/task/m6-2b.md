# M6-2b: positioned write と WAVE 書き経路

M6-2 の書き側単位。この文書は実装手順であり、完了条件は
[access.md](../access.md#m6-完了条件) の positioned write/spool 条項と
[media.md](../media.md#m6-完了条件) の WAVE mux 条項、contract 分類は
[scope.md](../scope.md#m6-の-contract-分類) を正本とする。

> 状態: **完了（2026-08-10）**

## 目的

M6-1 の file sink は入力 handle を順番に末尾へ書くだけであり、選択された `RandomWrite` は内部の
追跡 offset に対する `WriteAt` としてしか使われていない。WAVE mux は payload 終了後に RIFF/data
size を先頭へ patch する必要があるが、Format component は Provider の narrow view を受け取らず、
`Finalize` に emitter もない。

M6-2b は sink 側だけに append/absolute patch を表現する canonical item schema を導入し、mux が
graph と ownership を迂回せず header patch を下流へ渡せるようにする。さらに sequential-only sink
を Host-owned spool で実効的な random-write sink へ適応し、単位終了時に direct file と spool の
両方で正しい WAVE file を書ける状態にする。

## 決定

### 読み schema と書き schema を分ける

- source と Format read input は引き続き `access.Bytes()` を使う。
- sink と Format write output は、末尾追加と絶対 offset patch を区別する新しい canonical schema
  を使う。payload は `buffer.Handle`、offset は非負の byte offset とし、timestamp は持たない。
- item は ownership contract を持ち、`Share`/`Release`/layout size が payload handle と一致する。
  patch item も read-only で、sink が payload を変更しない。
- append marker を読み側 item へ持ち込まない。source 側に意味のない状態を載せると carrier contract
  が方向中立でなくなる。
- `internal/catalog` の trait 走査は、Access source output と Format read input を
  `access.Bytes()`、Format write output と Access sink input を新 schema として検証する。shape と
  schema の不一致は Host 構築時の composition diagnostic にする。

### mux は位置付き item だけを emit する

- WAVE mux は sink session、`Appender`、`Patcher` を直接受け取らない。header、audio data、padding は
  append item、確定後の size は absolute patch item として同じ output portへ渡す。
- `Finalize` は final size と patch payload を確定し、既存 lifecycle の `Flush` が emitter を使って
  patch item を流す。`Finalize` 自体へ emitter を追加しない。
- file sink は append item を `Appender`、patch item を `Patcher` へ適用する。選択された narrow
  view に必要な操作が無い場合は Open/Run の type assertion ではなく Prepare diagnostic にする。
- append の部分書き込み、patch の部分書き込み、offset overflow、payload ownership を一つの sink
  実装に集約し、Provider ごとに同じ dispatch を複製しない。

### WAVE header 長を後から変えない

- mux は RIFF header の先頭に `ds64` と同じ占有長の `JUNK` chunk を常に予約する。
- final size が RIFF の 32-bit 上限内なら `JUNK` のまま RIFF size/data size を patch する。上限を
  超えた場合は同じ範囲を `ds64` へ書き換えて RF64 にする。finalize 後に header 長を変えない。
- size 不明の `0xFFFFFFFF` を残した streaming WAVE は出力しない。random patch が使えない sink は
  spool するか、policy/quota diagnostic で拒否する。
- 4 GiB 境界は巨大 payload を実際に確保せず、header planner の累積 byte counter と pure marshal
  test で検証する。

### spool は Host-owned capability adapter とする

- WAVE write trait の意味上の要求は `RandomWrite` とする。`SequentialWrite` を同じ alternative に
  並べず、direct selection が失敗した後にだけ Host が sequential sink を random-writable spool で
  適応する。
- spool は graph component ではなく output boundary decorator である。media item を処理する第二の
  runtime、公開 temporary service、plugin の `OpenServices` 拡張を作らない。
- `job.ResourcePolicy` に spool の許可、最大 bytes、storage 種別を明示する。上限は最終 size が
  Compile 前に確定しないため `resource.Request`/`Grant` の予約次元へ入れず、Job-owned spool の
  局所 counter で強制する。
- storage と lifecycle は Host が所有し、cancel、Run failure、Finalize/Flush failure、commit failure、
  `Prepared.Close` のすべてで削除する。memory/disk の具体 storage は同じ adapter contract に従う。
- output session は M6-2a で確定した順序どおり resource reservation 後に acquire する。元 session の
  実 capability を再検証してから spool を被せ、format component には実効 capability を基に選んだ
  boundary を渡す。
- spool への patch がすべて終わった後、Host の sink Flush 段階で最終 byte 列を underlying
  sequential session へ一度だけ copy する。その後に Sync、PrepareCommit、Commit を行う。

### Plan は元 capability と適応結果を混ぜない

- `plan.Boundary.Available` は Provider/session が元から持つ capability を表す。
- 適応後の capability set を別 field で表し、`Selected` は Format 要求を実際に満たす実効 selection
  を表す。
- spool を使う boundary は `SpoolSpec` を別に持ち、storage、上限/予測 bytes、startup latency、final
  copy、rollback class を inert value として表示する。
- Plan fingerprint と validity は三者を区別する。同じ実効 capability でも direct と spool が同じ
  Plan にならないようにする。

## 手順

### 1. positioned write schema を追加する

- `access` に append/patch の closed operation と `buffer.Handle` payload を持つ item/schema を置く。
- constructor、validity、clone/ownership、offset の境界を unit test で固定する。
- raw PCM writer を append item の producer へ移し、source `Bytes()` との互換 alias は残さない。

### 2. catalog と file sink を新 schema へ移す

- Access/Format trait の方向別 port schema 検査を更新する。
- file sink operator を positioned item の唯一の dispatch point にし、append と patch を選択済み
  `Appender`/`Patcher` へ適用する。
- M6-1 の transactional replace、partial write、cancel、cleanup test を新 item contract で維持する。

### 3. WAVE mux を実装する

- `plugin/wave` に write component と `format.Write` trait を足す。
- RIFF/RF64 header planner と marshal を runtime operator から分け、size/padding/overflow を pure test
  できるようにする。
- mux operator は packet payload を append し、Finalize で size を確定し、Flush で fixed-offset patch
  item を emit する。payload handle の grant と release を failure path まで検査する。

### 4. spool policy と Plan projection を確定する

- `job.ResourcePolicy` に spool quota/storage を追加し、zero value、disabled、invalid combination を
  fail closed にする。
- `plan.Boundary` に original/effective capability と `SpoolSpec` を分けて追加し、clone、validity、
  fingerprint、redacted display を更新する。
- binder は direct capability selection を先に行い、失敗した output boundary だけを policy に従って
  adapter candidate として再評価する。

### 5. Host-owned spool adapter を実装する

- selected output opening を random-writable spool で decorate し、underlying sequential transaction
  の ownership を同じ prepared scope に登録する。
- quota は write/patch 後の logical extent に対して検査し、sparse offset や整数 overflow で回避
  できないようにする。
- final copy、Sync、PrepareCommit、Commit、Abort/Close の順と failure aggregation を Host の既存
  lifecycle へ統合する。

### 6. direct と spool の WAVE 出力を通す

- random-write file sink へ PCM を WAVE mux して、標準 reader でも再読できる RIFF/RF64 file を作る。
- sequential-only fixture sink へ同じ Job を流し、spool 経由の byte 列が direct 出力と一致することを
  検査する。
- quota 超過、spool storage failure、final copy failure、commit failure、cancel の各経路で target と
  temporary storage が正しい状態に残ることを固定する。

## 検証

```bash
go test ./access/ ./job/ ./plan/ ./host/ ./internal/bind/ ./internal/catalog/ ./plugin/file/ ./plugin/pcm/linear/ ./plugin/wave/ -race
go vet ./access/ ./job/ ./plan/ ./host/ ./internal/bind/ ./internal/catalog/ ./plugin/file/ ./plugin/pcm/linear/ ./plugin/wave/
go build ./...
gofmt -l .
go run ./tools/cmd/docs-check
```

追加で次を検査する。

- source/read trait は `access.Bytes()`、write trait/sink は positioned schema でなければ composition が
  失敗する。
- mux が Provider view を直接取得せず、header patch が graph queue と ownership contract を通る。
- RIFF/RF64 の 32-bit 境界、odd-size padding、`JUNK`/`ds64` 置換で header 長が一定である。
- Plan から元 capability、不足、適応後 capability、selection、SpoolSpec が別々に読める。
- spool quota は最大 extent を越える前に deterministic に失敗し、cancel/failure/Close 後に memory と
  disk storage を残さない。

**単位完了 gate:** PCM から実 WAVE file を書く end-to-end test と、sequential-only sink へ spool
経由で同じ正しい WAVE byte 列を書く test がともに green である。RIFF INFO、未知 chunk preservation、
Binding 駆動選択は M6-2c、自動 Format 判別は M6-3 へ残す。

## 実装結果

- `access.Writes()` は append/absolute patch を `buffer.Handle` ownership とともに表現し、Format write
  output と Access sink input の canonical schema になった。catalog は source/read の
  `access.Bytes()` と write/sink の `access.Writes()` を方向別に検証する。
- linear PCM writer と WAVE mux は Provider view を取得せず positioned item を emit し、file sink が
  `Appender`/`Patcher` への部分書き込みを一か所で処理する。WAVE mux は固定長の `JUNK`/`ds64`
  header を使い、Finalize 後の Flush で RIFF/RF64 size patch を同じ graph queue へ流す。
- spool policy、元/実効/選択 capability、`SpoolSpec` は Job と Plan の別々の値として固定した。binder
  は direct `RandomWrite` を常に優先し、許可された sequential-only output にだけ spool adaptation を
  Plan する。
- Host-owned memory/disk spool は logical extent に quota を適用し、underlying Provider からは
  `SequentialWrite`、Format component からは実効 `RandomWrite` として見える。最終 byte 列は sink
  Flush で一度だけ copy され、その後に Sync/PrepareCommit/Commit が行われる。
- direct file と memory/disk spool の WAVE byte 列一致、Plan projection、partial final copy、quota、
  storage/copy/commit failure、cancel、temporary cleanup を unit/end-to-end test で固定した。指定 package
  の race test と vet、全 package build、format check は green である。
