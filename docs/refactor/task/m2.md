## スコープ

**やること**: foundation package の新設のみ。

**やらないこと**:

- `core`、`sdk`、`plugin/<family>`、`cli`、`bindings`、`example` の変更。旧経路はそのまま動かし続ける。
- 公式 plugin の marker identity 移行（M6/M8）、旧 registry/generator の削除（M8/M11）。
- port、`Compile`、`Open`、`Suggest`、variant、Plan、Run に関わる型（M3〜M5）。

新 package は旧 package から参照されない独立した層として育てる。旧経路との接続は M6 の縦断経路で初めて行う。将来の phase 用に空の field、placeholder interface、TODO 付きの型を先回りして作らない。

## package 配置

root module (`github.com/godexture/godec`) に置く。`go.work` の変更は不要。

```text
diagnostic/          code、severity、path、item、集約
config/              Schema、field、Codec、Patch、Resolved、Provenance、Fingerprint
plugin/              Identity、Descriptor、Component、Definition、Set
internal/catalog/    検証済み immutable index
host/                New、option、Catalog view
```

`plugin/` は既存の公式 plugin family directory である。その直下に foundation の `package plugin` を追加し、`plugin/flac` 等の subdirectory には触れない。`net` と `net/http` と同じ構成であり、後の family module split とも両立する。

package 名は複合語を避ける（AGENTS.md Rules）。

## 作業単位と手順

単位ごとに独立して review・commit できる粒度を保つ。各単位は「実装 → その package の test → 次へ」の順で進め、単位をまたいで未完成の型を残さない。

### 1. `diagnostic`

structured diagnostic の最小 contract。以降の全 package が依存するため最初に作る。

- item は stable な code、severity、対象 path（component identity と field path を表現できる構造）、人間向け message、追加 detail を持つ。
- 複数 item を集約して一つの error として返せる。最初の一件で打ち切らない。
- code は文字列 message ではなく安定した識別子とし、surface が別表現へ投影できるようにする（[runtime.md](../runtime.md) の「panic と error」）。
- secret を保持しない。redaction の責務は値を作る側にあることを godoc に明記する。

### 2. `config` (a) 骨格

- `Schema[C]` の builder、typed field accessor（`func(*C) *T` 形）、default 生成関数、preset、`Validate`。
- 疎な `Patch` と、`Value`/`Provenance`/`Diagnostics`/`Fingerprint` を持つ `Resolved[C]`。
- 解決 pipeline を [config.md](../config.md#解決順序) の順序どおり一本で実装する。優先順位は `default < preset < explicit`。
- builder の正確な API 名と error 表現は実装者が決めてよい（config.md が明示的に実装時判断としている）。ただし次は守る。
  - schema 構築 error は panic せず builder が保持し、`plugin.Define`/`host.New` が aggregate error として報告する。
  - `Schema.Default()` は呼び出しごとに fresh な値を返す。slice、map、pointer、function を含む nested field も snapshot 化する。exported な default 変数を作らない。
  - 完全値 `C` と `Patch` を混同できない型にする。unknown field は error。
- control plane で `Schema[C]` を型消去する interface をこの package に置く。catalog が保持するのはこの erased view であり、data plane では使わない。

### 3. `config` (b) field 型

[config.md](../config.md#field-type-と-codec) の標準型と第三者 `Codec[T]` を実装する。単位付き値（duration、byte size、frequency、ratio、decibel）、enum、optional/auto を表す sum type、nested struct、ordered slice、discriminated union、secret を扱えるようにする。

入力依存の `auto` は `Rate` 相当の明示 sum type として型で表す。実効値の解決は `Compile` の責務なので M2 では行わない。

### 4. `config` (c) canonicalization と fingerprint

- canonical encoding は map iteration order、registration order、pointer address に依存しない。field ID 順序と nested collection の順序を定義する。
- fingerprint は domain 分離した安定 hash とし、同じ値なら process を再起動しても一致する。hash algorithm は実装者が選んでよいが、選定理由を godoc に一行残す。
- canonical form を作れない field は schema 登録を失敗させる。
- secret の raw value を canonical 表現、fingerprint 入力、diagnostic のいずれにも露出させない。
- schema resolve と canonicalization の代表 benchmark を追加する。判定は [performance.md](../performance.md#開発時の性能回帰方針) に従い、絶対値ではなく明白な回帰の検出に使う。

### 5. `plugin`

- marker type の Go type identity から canonical identity を導出する。identity に version、display name、config 型、alias を含めない。
- component definition は M2 では不透明にする。持つのは component の marker identity、descriptor、型消去した config schema、alias だけとする。port、`Compile`、`Open` の field や interface をこの時点で作らない。M3/M4 で追加する。
- component 用の型は `plugin` package 内に置く。`component` package の新設は Spec/port/Compile が入る M3 で行う。
- plugin descriptor は [plugins.md](../plugins.md#descriptor-と配布情報) の項目を保持できるようにする。SBOM/provenance の検査自体は M10。
- `Set` は immutable な persistent value とし、`Add`/`Remove`/`Override` が元の値を変更せず新しい値を返す。
- 同じ marker identity の二重追加は error。last-wins にしない。置換は対象 identity を指定する `Override` だけで行う。
- package-level mutable state と `init` による副作用登録を持たない。
- 公式 plugin が definition を返す API の形は関数形（`flac.Plugin()`、`flac.Codec()`）に確定した。この package の godoc と example もその形で書く。実際の公式 plugin の移行は M6/M8。

### 6. `internal/catalog`

- `Set` から検証済みの immutable index を作る。
- invalid entry を黙って除外せず、構築失敗にする（F28）。「未導入」と「壊れた plugin」を区別できる diagnostic を返す。
- 検証対象は identity の重複、descriptor の欠落、config schema の構築 error、alias の妥当性。port と `Compile` の検証は M3/M4 で追加する。
- 構築後に内容が変わらないことを型で保証する。read API は copy を返すか、変更できない view を返す。

### 7. `host`

- `host.New(host.Plugins(set))` で catalog を構築し、失敗を aggregate error で返すところまで。
- 公開するのは catalog view と構築 error だけとする。`Close`、`Prepare`、`Plan`、`Run` は resource と planner が入る M4/M5 で追加するため、この時点で export しない。
- 複数の `Host` を同一 process で構築しても catalog、default、state が互いに影響しないことを保証する。

## test

各単位の package に unit/property test を置く。公式 plugin を import しない。test 用の plugin/component/config は foundation test 内の fixture として定義する。

[quality.md](../quality.md#foundation-test) の一覧のうち、M2 で該当するのは次である。

- marker identity、duplicate、explicit override
- config default/preset/patch、canonicalization、fresh snapshot
- invalid schema/definition の aggregate error（component identity と field path を含むこと）
- canonical fingerprint が map/registration order と process 再起動に依存しないこと
- 複数 Host の catalog/default/state isolation
- secret が `Resolved` の公開表現、diagnostic、error に出ないこと

map iteration order と registration order を意図的に乱す test を含める。race test を実行する。

## 検証

[AGENTS.md](../../../AGENTS.md) の Tools と [quality.md](../quality.md#開発時の検証-tier) に従う。

- 単位ごと: 対象 package の test。例 `go test ./config/... ./plugin/... -race`
- 単位ごと（新 package が root module の build を壊していないこと）: `go build ./...`
- M2 完了確認時のみ: `go run ./tools/cmd/test-runner --simd`

benchmark は単位 4 の canonicalization/fingerprint だけで取る。data plane を変更しないため、それ以外で full matrix を実行しない。

## 中断して確認する条件

AGENTS.md の規約どおり、次の場合は独断で決めずに実装を止めてユーザーへ確認する。

- 参照文書の記述どうしが矛盾する、または M2 の完了条件を満たす方法が複数あり、どちらも public contract の形を変える。
- 新 package の contract を成立させるために、`core`/`sdk`/`plugin/<family>` の変更が必要だと判断した。
- M3 以降の型（port、`Compile`、schema、Plan）を先に決めなければ M2 が完成しないと判明した。
- [decisions.md](../decisions.md) にない product 判断が必要になった。この場合は decision ledger の「更新規則」に従い、確認待ちとして記録する。

## 完了時の記録

1. [plugins.md](../plugins.md#m2-完了条件) と [config.md](../config.md#m2-完了条件) の完了条件を逐条で確認する。満たせない項目があれば完了にせず報告する。
2. `go run ./tools/cmd/test-runner --simd` を実行する。
3. [checkpoint.md](../checkpoint.md) の M2 行を更新する。更新規則はその文書の冒頭に従い、benchmark の単発値や test log を残さない。
4. M3 以降へ送る未完了事項があれば、この文書ではなく該当設計資料または checkpoint の注記へ書く。
