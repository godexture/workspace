# MP3デコーダ独自実装 開発ドキュメント

## 概要

`plugins/codec-mp3` において、完全な独自のGo実装によるMP3デコーダを新規に構築する。
最終的には外部のC言語ライブラリに依存せず、GoのみでMP3のデコードを実現する。

> **既存実装の扱い**  
> 現在 `plugins/codec-mp3` は `github.com/hajimehoshi/go-mp3` を用いた実装が存在するが、
> 本プロジェクトではそれを無視し、`minimp3.h` を起点とした実装を**新規に**構築する。
> 既存の `go-mp3` 依存は、全ステップ完了後に `go.mod` / `go.sum` から削除する。

---

## 開発ステップ

開発は以下の4つのステップに分けて段階的に進める。

### 1. minimp3 の導入 (CGO経由)

- CC0ライセンスのシングルヘッダMP3デコーダである [`minimp3.h`](https://github.com/lieff/minimp3) をプロジェクトに導入する。
  - 取得元: `https://github.com/lieff/minimp3`（`minimp3.h` および `minimp3_ex.h` の2ファイル）
  - バージョン: 取得時のコミットハッシュをドキュメントに記録しておく。
- CGOを用いて `minimp3.h` をビルドし、Goから呼び出せる状態にする。
- **この時点でスナップショットテストを構築し、以降のステップのベースラインとする（詳細は「テスト・検証戦略」を参照）。**

### 2. Goによるラッパーの実装

- `minimp3` で提供されている各関数や構造体に対して、Go言語のラッパー関数・型を定義する。
- この段階では、ラッパー関数の中身は単純にCGO経由で `minimp3` の関数を呼び出すのみとする。
- ラッパーが動作すること（スナップショットテストでビット一致すること）を確認してから次のステップへ進む。

### 3. 役割ごとのファイル分割

- **ステップ2のGoラッパーが完成した後**に行う。
- ラップした各関数や構造体を、役割（例えばヘッダ解析、ハフマン復号、逆量子化、IMDCT、合成フィルタなど）ごとに適切な複数のGoファイルに分割・整理する。
- ファイル分割後もスナップショットテストが通ることを確認する。
- 見通しの良いコードベースを構築し、次のステップ（各関数の独自Go実装）に備える。

### 4. 独自のGo実装への置き換え

- 分割した各関数を、一つずつ `minimp3` のC言語の実装を参考にしながら、独自のGo実装に置き換えていく。
- 置き換えが完了した部分はCGOへの依存を削除し、最終的に全ての処理をGo言語のみで完結させる。
- 各関数を置き換えるたびにスナップショットテストを実行し、リグレッションがないことを確認する（比較方式は「テスト・検証戦略」を参照）。

## テスト・検証戦略

独自実装への置き換え（ステップ4）を安全かつ確実に行うために、以下のテスト戦略を導入する。

### テスト用MP3ファイルの要件

著作権フリー（CC0またはパブリックドメイン）の音声ファイルを複数用意し、幅広いバリエーションをカバーする。

| バリエーション | 例 |
|---|---|
| MPEG規格 | MPEG1 / MPEG2 / MPEG2.5 |
| ビットレート種別 | CBR（固定） / VBR（可変） |
| チャンネル | モノラル / ステレオ / Joint Stereo |
| ビットレート | 64kbps / 128kbps / 192kbps / 320kbps 程度 |
| サンプリングレート | 44100Hz / 48000Hz / 22050Hz など |
| 特殊ケース | 無音・極端に短いファイル・Xingヘッダ付きVBR など |

調達先の例:
- [freesound.org](https://freesound.org)（CC0フィルタで検索）
- [ccmixter.org](https://ccmixter.org)
- Wikipedia上のMP3サンプル

### スナップショットテストの構築

**ステップ1（minimp3の導入）が完了し、動作した時点**で、テストの基準となるスナップショットを作成する。
- 用意した複数のMP3音声ファイルを入力とし、デコード結果（PCMデータ）をバイナリスナップショットとして保存する。
- スナップショットはリポジトリに `testdata/snapshots/` などとしてコミットする。

### リグレッションの防止：フェーズごとの比較方式

コードに変更を加えるたびに、デコード結果とスナップショットを比較する。
比較方式はステップによって異なる。

| ステップ | 比較方式 | 理由 |
|---|---|---|
| ステップ2（Goラッパー） | **完全ビット一致** | CGO経由でCを呼ぶため結果は同一のはず。差異があれば実装バグ。 |
| ステップ3（ファイル分割） | **完全ビット一致** | リファクタリングのみで処理内容は変わらないため。 |
| ステップ4（Go化） | **Epsilon許容比較** | CとGoの浮動小数点演算の差異（丸め誤差）が生じうるため。 |

> ステップ4のEpsilonの値は `実装上の注意事項 - 3. 浮動小数点演算と型の差異` を参照。

## ライセンスについて

### minimp3

`minimp3` は [lieff/minimp3](https://github.com/lieff/minimp3) が公開しているシングルヘッダライブラリであり、**CC0 1.0 Universal（パブリックドメイン相当）**で提供されている。
プロジェクトに `minimp3.h` を同梱する場合は、ヘッダ内のライセンス表記をそのまま保持すること。

### テスト用音声ファイル

テストデータとして使用する音声ファイルはすべて CC0 またはパブリックドメインのものを使用する。
各ファイルの出典・ライセンスを `testdata/README.md` 等に明記しておくこと。

## 実装上の注意事項

C言語（`minimp3`）からGo言語への移植においては、以下の点に注意して実装を行う。

### 1. ポインタ演算からスライス操作への変換

C言語のコードではポインタ演算（例：`ptr++` や `ptr + offset`）が多用されているが、Goでは `unsafe.Pointer` を極力避け、**スライスとそのインデックス（`slice[offset:]`）を使った操作**に翻訳する。この際、境界外アクセス（Out of bounds）によるパニックが起きないよう、正確なインデックス管理を行う。

### 2. 符号付き・符号なし整数のビットシフト

MP3のハフマン復号やヘッダ解析ではビット演算が多用される。Goへ移植する際、特に**右シフト（`>>`）**に注意する。Goでは左辺が符号付き整数の場合は算術シフト（符号拡張）、符号なし整数の場合は論理シフト（0埋め）となるため、適切な型（`uint32` や `uint8` など）を厳密に使い分ける。

### 3. 浮動小数点演算と型の差異

Cの `float` は Goの `float32` に相当するが、コンパイラの最適化やハードウェアのFPUの扱い方の違いによって、微小な演算誤差が生じる可能性がある。スナップショットテストにおいて「浮動小数点の誤差を許容する」のはこのためであり、比較時には許容誤差（Epsilon）の値を適切に設定して検証を行う。

Epsilonの目安として、まず `1e-5`（`float32`で約5桁の有効数字）程度から始め、テストの結果を見ながら調整する。

### 4. パフォーマンスチューニングは後回しにする

C言語はSIMD命令などを駆使したコンパイラ最適化が強力に効くが、Goへの単純なベタ移植の段階ではパフォーマンスが落ちる可能性がある。最初から最適化を意識しすぎるとバグを生む原因になるため、**「まずはスナップショットテストを通す（正しさの担保）」**ことに集中する。すべてGo化が完了した後にプロファイリング（`pprof`）を行い、ボトルネック（IMDCTや合成フィルタなど）の最適化（境界チェックの省略、ループ展開、必要であればGo Assemblyの導入など）を検討する。
